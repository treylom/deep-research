# AC6 도메인 테스트 3종 — 고정 질의 (fixture)

> AC6 = "기존 대비 **rubric 동등 이상 · 시간 단축 · A급+ 분포 개선**" 3축 비교. 이 파일은 그 비교의
> **입력을 고정**한다 — 질의가 실행마다 바뀌면 두 공정을 비교한 게 아니라 두 질문을 비교한 것이 된다.
>
> ⚠️ **이 3종은 서로 다른 유형이어야 한다.** 같은 유형 3개는 프레임 표의 한 행만 반복 시험하고,
> 유형 라우팅(§3)은 한 번도 시험되지 않는다.
>
> 실행 규약: 각 질의를 **신 공정 1회 + 구 공정(baseline) 1회**, 같은 기기·같은 날. 산출은
> `out/report.md` · `out/sources.jsonl` · `out/meta.json`(아래 계약) 3파일.

## meta.json 계약 (시간 축의 유일 측정면)

```json
{ "query_id": "D1", "process": "searchflow|legacy",
  "started_at": "2026-07-31T09:00:00+09:00", "ended_at": "2026-07-31T09:12:31+09:00",
  "rounds": 1, "workers": 4, "stop_reason": "success|deadline|cancel" }
```

시간을 사람이 눈으로 적으면 비교가 안 된다. **`meta.json` 이 없으면 시간 축은 "측정 불가"** 이며,
그것을 "동등"으로 적지 않는다(0 의 두 얼굴 — 미측정과 무차이는 다르다).

## D1 — factcheck (단일 주장 참·거짓)

> HTTP 418 "I'm a teapot" 은 현행 HTTP 표준에 등록된 상태 코드인가?

- 완료 조건: 판정(참·거짓·부분) + 1차 원문(표준 문서 발행처) 인용 + 반증 축 별도 조사.
- 이 질의를 고른 이유: 답이 **표준 문서로 확정 가능**해서 채점자 재량이 최소다. AC8 완주 시험과 같은 질의라 산출 2건이 이미 있다.

## D2 — compare (둘 이상 대안의 축별 대조)

> 파이썬 패키지 관리에서 `uv` 와 `pip` 는 **의존성 해석 방식**이 어떻게 다른가?

- 완료 조건: 축을 먼저 세우고(해석 알고리즘·잠금 파일·재현성) 축별 대조표 + 각 축의 1차 근거(공식 문서·소스).
- 이 질의를 고른 이유: **축 설계 실패**가 바로 드러난다. 축 없이 장단점을 나열하면 compare 유형이 discovery 로 퇴화한 것이다.

## D3 — tech (구조·동작 원리 설명)

> `git` 의 `rebase` 는 커밋 객체를 어떻게 처리하는가 — 이동인가 재생성인가?

- 완료 조건: 객체 모델 수준 설명 + 공식 문서·소스 인용 + "이동"이라는 흔한 오설명에 대한 명시적 정정.
- 이 질의를 고른 이유: **흔한 오설명이 존재**해서, 검색 상위에 오답이 많다. 출처 등급이 실제로 작동하는지 시험된다.

## 이 fixture 가 담보하지 않는 것

- **3종은 작은 표본이다.** 3종 통과를 "공정이 더 좋다"로 읽으면 안 된다. 읽을 수 있는 것은
  "이 3종에서는 열세가 아니었다"까지다.
- 유형 8종 중 3종만 시험한다 — person·policy·market·company·discovery 는 미시험 축이다.
- 채점 가중치가 확정 전이면 rubric 축 비교는 **잠정 가중치 기준**이다(라벨로 명시할 것).
